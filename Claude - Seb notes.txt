The Claude API follows a request–response model. Each request to the Claude Messages API includes:

{
  "model": "claude-sonnet-4-6",
  "max_tokens": 1024,
  "system": "You are a helpful assistant.",
  "messages": [
    {"role": "user", "content": "Hi!"},
    {"role": "assistant", "content": "Hello!"},
    {"role": "user", "content": "How are you?"}
  ],
  "tools": [...],
  "tool_choice": {"type": "auto"}
}


tool_use is a mechanism that allows Claude to call external functions. The model does not run code directly—it generates a structured tool call request; your code executes it and returns the result.

Each tool is defined using a JSON schema:

{
  "name": "get_customer",
  "description": "Finds a customer by email or ID. Returns the customer profile, including name, email, order history, and account status. Use this tool BEFORE lookup_order to verify the customer's identity. Accepts an email (format: user@domain.com) or a numeric customer_id.",
  "input_schema": {
    "type": "object",
    "properties": {
      "email": {"type": "string", "description": "Customer email"},
      "customer_id": {"type": "integer", "description": "Numeric customer ID"}
    },
    "required": []
  }
}

1. Send a request to Claude with tools
2. Receive a response
3. Check stop_reason:
   - "tool_use" -> execute the tool, append the result to history, go back to step 1
   - "end_turn" -> the task is complete, show the result to the user
4. Repeat until completion

The Model Context Protocol (MCP) is an open protocol for connecting external systems to Claude. MCP defines three primary resource types:
Tools — functions the agent can call to perform actions (CRUD operations, API calls, command execution)
Resources — data the agent can read for context (documentation, database schemas, content catalogs)
Prompts — predefined prompt templates for common tasks

An MCP server is a process that implements the MCP protocol and provides tools/resources. When you connect to an MCP server:
All tools are discovered automatically
Tools from all connected servers are available at once
Tool descriptions determine how the model will use them

 Maximum import nesting depth is 5 - what does this mean

It means imports can chain through at most 5 levels: a file imported by your CLAUDE.md can import another file, and so on, up to 5 times. Anything deeper doesn't load.

Here's an example chain starting from your project:

CLAUDE.md
 └─ @standards/coding-style.md          ← level 1
     └─ @standards/python.md             ← level 2
         └─ @standards/naming.md         ← level 3
             └─ @standards/variables.md  ← level 4
                 └─ @standards/consts.md ← level 5 ✅ loads
                     └─ @standards/x.md  ← level 6 ❌ ignored

- Depth means a chain, not a count. Your CLAUDE.md can import 20 files directly, and they're all level 1. The limit only applies to imports inside imports.
- Why it exists: it stops runaway or circular imports, such as A importing B and B importing A, and keeps context from growing without bound.
- In practice: if a rule seems to be ignored and it sits deep in an import chain, run /memory to check whether it loaded. Then flatten the chain by importing that file straight from CLAUDE.md.

Exam angles:
- Subagents don't inherit the parent's context. Anything the subagent needs must go into its task prompt. A frequent wrong answer assumes the subagent "already knows" earlier findings.
- Context protection: subagents keep verbose work, like reading many files, out of the coordinator's context. Only the summary comes back. This ties to Domain 5, Context Management.
- Choosing between them: "compare alternatives from the same baseline" points to fork. "Parallelize or isolate subtasks within one job" points to subagents.

Explicit Criteria vs Vague Instructions:
CRITICAL: Runtime failure for users
  Example: NullPointerException while processing a payment

HIGH: Security vulnerability
  Example: SQL injection, XSS, missing authorization checks

MEDIUM: Logic bug without immediate impact
  Example: Wrong sorting, off-by-one error

LOW: Code quality
  Example: Duplication, suboptimal algorithm for small data
  

Prompt chaining breaks a complex task into a sequence of focused steps:

Step 1: Analyze auth.ts (local issues only)
       -> Output: list of issues in auth.ts

Step 2: Analyze database.ts (local issues only)
       -> Output: list of issues in database.ts

Step 3: Integration pass (cross-file dependencies)
       -> Output: issues at module boundaries
Why this matters:

Avoids attention dilution—when the model receives too many files at once, it may miss bugs in some files while providing shallow commentary on others
Ensures consistent analysis quality per file
Allows separate analysis of cross-file interactions

When to use prompt chaining vs dynamic decomposition:

Prompt chaining — predictable, repeatable tasks (code review, file migrations)
Dynamic decomposition — open-ended investigations where subtasks become clear only during execution

When extracted data fails validation:

Step 1: Extract data from the document
Step 2: Validate (Pydantic, JSON Schema, business rules)
Step 3: If there's an error—retry with context:
  - The original document
  - The previous (incorrect) extraction
  - The specific error: "Field 'total' = 150, but sum(line_items) = 145. Re-check values."

Pydantic as a validation tool: Pydantic is a Python library for schema-based data validation. For the exam, the key points are:

Structural validation: types, requiredness, enum constraints checked in code after receiving JSON from Claude
Semantic validation: custom validators enforce business logic (sum of items equals total; start_date < end_date)
Validate–retry loops: on Pydantic validation failure, construct an error message and re-prompt Claude with the error context
JSON Schema generation: Pydantic models can generate JSON Schema for tool_use, providing a single source of truth

A short sketch of steps 3 and 5 in Python:

failed = []
for r in client.messages.batches.results(batch_id):
    if r.result.type == "succeeded":
        save(r.custom_id, r.result.message.content)
    else:
        failed.append(r.custom_id)

retry_requests = [
    {"custom_id": f"{doc_id}-part{i}", "params": build_params(chunk)}
    for doc_id in failed
    for i, chunk in enumerate(split_into_chunks(docs[doc_id]))
]
client.messages.batches.create(requests=retry_requests)

The context limit applies to each request separately, not to the whole batch. If one document plus your prompt plus the room reserved for output (max_tokens) is bigger than the model's context window, that request can never fit. Splitting the document creates several smaller requests, and each one fits within its own window.

Before:  1 request = prompt + 1.3M-token document   → ❌ over the 1M limit

After:   request A = prompt + chunk 1 (450K)        → ✅
         request B = prompt + chunk 2 (450K)        → ✅
         request C = prompt + chunk 3 (400K)        → ✅

7.5 SLA Planning
If you need a result in 30 hours and the Batch API can take up to 24 hours:

Submission window: 30 - 24 = 6 hours
Batches must be submitted no later than 24 hours before the deadline
For frequent submissions, split into 4-hour windows

The planning rule is to work backwards from the deadline. The Batch API promises results within 24 hours, so a batch is only safe if it's submitted at least 24 hours before you need the results.

Using a deadline 30 hours from now:

Now (hour 0)            Hour 6                              Hour 30
|---- submit window ----|------- worst-case processing -----|
       6 hours                     24 hours              DEADLINE

- A batch submitted at hour 0 finishes by hour 24 at the latest, which is safe.
- A batch submitted at hour 6 finishes by hour 30 at the latest, which just makes it.
- A batch submitted at hour 7 might finish at hour 31, which misses the deadline.

Prompt Chaining
Document -> Metadata extraction -> Data extraction -> Validation -> Enrichment -> Final output
That's a fixed sequential pipeline, also called prompt chaining. It's covered in Chapter 8.1 of the guide and in exam Domains 1 and 4. Each stage is a separate, focused step, and its output becomes the next stage's input.

┌─────────────────────┬────────────────────────────────────────────────────────────────────────────────┬────────────────────────────────────────────────────┐
│        Stage        │                                    Purpose                                     │                 Example (invoice)                  │
├─────────────────────┼────────────────────────────────────────────────────────────────────────────────┼────────────────────────────────────────────────────┤
│ Metadata extraction │ Work out what the document is                                                  │ Type = invoice, vendor = Acme, date, language      │
├─────────────────────┼────────────────────────────────────────────────────────────────────────────────┼────────────────────────────────────────────────────┤
│ Data extraction     │ Pull structured fields, using the metadata to choose the schema                │ Line items, totals, tax, PO number                 │
├─────────────────────┼────────────────────────────────────────────────────────────────────────────────┼────────────────────────────────────────────────────┤
│ Validation          │ Check the extracted data: schema-valid, totals add up, required fields present │ Do the line items sum to the total?                │
├─────────────────────┼────────────────────────────────────────────────────────────────────────────────┼────────────────────────────────────────────────────┤
│ Enrichment          │ Add data from outside the document                                             │ Look up the vendor ID in the CRM, convert currency │
├─────────────────────┼────────────────────────────────────────────────────────────────────────────────┼────────────────────────────────────────────────────┤
│ Final output        │ Produce clean, structured JSON for downstream systems                          │ A record ready to write to the database            │
└─────────────────────┴────────────────────────────────────────────────────────────────────────────────┴────────────────────────────────────────────────────┘

Why split it up instead of using one large prompt?
- Focus: each prompt does one job, which makes it more accurate and easier to tune.
- Debugging: when output is wrong, you can see which stage caused it.
- Mixed tools: some stages don't need an LLM at all. Validation can be plain code, and enrichment can be an API call.
- Cost: a cheaper model or lower effort can handle the simpler stages.

The validation stage carries the most weight on the exam:
- Syntax errors (bad JSON, wrong types): prevent them with structured outputs or strict: true tool schemas.
- Semantic errors (valid JSON with wrong values, such as totals that don't add up): only validation catches these.
- When validation fails, retry with feedback: send the specific error back to the extraction stage ("Line items sum to 950 but total says 1000; re-check"), not just "try again" (Chapter 6.5).
- After N failed retries, escalate to human review instead of passing bad data along (Chapter 9).

Fixed versus adaptive:

┌─────────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────────────┐
│                  Use a fixed pipeline when                  │         Use adaptive decomposition (Chapter 8.2) when          │
├─────────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────────────┤
│ The steps are known in advance and the same for every input │ The steps depend on what's discovered along the way            │
├─────────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────────────┤
│ Example: invoice processing, form extraction                │ Example: open-ended research, debugging an unfamiliar codebase │
├─────────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────────────┤
│ Predictable, testable, cheaper                              │ Flexible, but less predictable                                 │
└─────────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────────────┘

Exam rule of thumb: a known, repeatable process calls for a fixed pipeline in code. Reach for an agent only when the path can't be specified ahead of time.


Separate context layer: In multi-agent systems, each subagent operates within a limited context budget—it receives only the information required for its task. The coordinator acts as a separate context layer: it aggregates subagent outputs, stores global state, and allocates context. This prevents “context leakage,” where one agent consumes the window with information irrelevant to others.
